WARA — enumerated source for the Well-Architected Reliability Assessment (APRL-backed) ​

Enumerated 2026-11-25. Verification method and limits are stated below — read them before quoting any coverage number from this page.

Microsoft's Well-Architected Reliability Assessment (WARA) is an automated review of a workload's reliability. Its tooling runs the Azure Resource Graph queries that the Azure Proactive Resiliency Library (APRL) publishes for each Azure resource type, and turns the hits into an action plan. src/assess/rules/wara.reliability.yaml does the same job from the data Scout has already collected into collect.json, so it needs no extra Azure call and no extra permission. It is written against this page only, and every rule cites an item number from the tables below.

Rules were NOT run against a live tenant for this page.

Is APRL current, or has it been merged into something else? ​

Checked 2026-11-25, and no, it has not been merged or retired:

  • The APRL repository (Azure/Azure-Proactive-Resiliency-Library-v2) is not archived, is licensed MIT, describes itself as the "source for Azure WAF reliability guidance and associated ARG queries", and was last pushed on 2026-11-23. Its README sends readers to the GitHub Pages site (aka.ms/aprl) unless they want to contribute. No deprecation or merge notice was found.
  • The WARA tooling repository (Azure/Well-Architected-Reliability-Assessment) is not archived, is MIT licensed, and was last pushed on 2026-11-23. Its module has three commands: Start-WARACollector, Start-WARAAnalyzer and Start-WARAReport. The collector needs PowerShell 7.4 and the Az modules; the report step needs Windows with PowerPoint.
  • Microsoft Learn's prose side of the same material is the reliability guides by service index (dozens of services, each with production-deployment, zone-failure, region-failure and maintenance sections). APRL recommendations link to those guides; the guides did not absorb APRL.
  • Learn's Reliability in Azure page now also points at AI-assisted reliability services (Azure Resiliency capabilities, a resiliency agent in Azure Copilot, Azure SRE Agent). These sit alongside APRL; none of them replaces its query library.
  • Azure Advisor's reliability recommendations overlap with APRL (some APRL items carry an Advisor recommendationTypeId), which is why the WARA module "uses outputs from the Azure Well-Architected Framework and Azure Advisor". Scout scores Advisor separately in advisor-recommendations.md.

The one thing this enumeration is NOT ​

It is not APRL, and it is not Microsoft's WARA score. APRL holds a large number of recommendations across more than 100 provider folders, most of them about configuration Scout does not collect (child resources, metrics, Kubernetes objects, guest settings) or about application behaviour (retries, connection reuse) that no inventory can see. This page covers the subset whose condition maps to a property Scout collects, plus one Manual item (WARA-ER-02) that attaches the nearest evidence. APRL's own queries also differ in two ways Scout cannot match today: they filter to a region list that has availability zones, and they read properties Scout's slimmer projections omit. Where Scout is coarser, the rule's remediation says so.

APRL is MIT licensed. Nothing here is copied from it: titles and remediation are Scout's wording, and each item cites the APRL recommendation it paraphrases by aprlGuid and repository folder. The aprlGuid is also the file name of the recommendation's query (kql/<aprlGuid>.kql), so a reader can check any item against the source. Folder URLs are of the form https://github.com/Azure/Azure-Proactive-Resiliency-Library-v2/tree/main/azure-resources/<Provider>/<type>.

Every item is gated on its own resource type existing: an estate without that service reports it Not assessed, never passed. "Impact" is APRL's own rating for the recommendation; "Severity" is what Scout's rule uses, lowered where the condition cannot tell production from test.

How null and missing values are read ​

A count Resource Graph reports as null (for example zoneCount on a resource with no zones array) means "none", and a null or empty haMode, tier or zonalAllocationPolicy is read the way ARM defaults it (HA Disabled, AKS tier Free, no zonal allocation). JSONPath compares null as lower than any number, so zoneCount < 2 lists both 0 and null. A property that is missing from the row altogether matches no comparison, so a missing key is never listed; Scout always writes the key.

Two rules (WARA-ASP-02 and WARA-REDIS-01) mix && and || in one filter. Newtonsoft JSONPath has no parentheses and nests the later operator to the right, so a && b || c reads a && (b || c) and a || b && c reads a || (b && c). tests/Assessment.WaraAdvisor.Tests.ps1 pins both results.

What a "Not assessed" or "Manual" result means here ​

  • Not assessed — the resource type is absent from the collected estate (or its dataset was not collected). Nothing was checked.
  • Manual — Scout found resources of that type and attached them as evidence, but the property that decides the question is not collected. Open each listed resource and answer the item by hand.
  • Pass / Fail — the property was collected and the condition was evaluated for every listed resource. A Fail names the resources; read the remediation for the exceptions Scout cannot see (non-zone regions, test environments).
