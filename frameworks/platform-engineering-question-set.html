Platform Engineering — enumerated source for the Platform Engineering Technical Assessment ​

Enumerated 2026-11-25. Verification method and limits are stated below — read them before quoting any coverage number from this page.

Scout's platform.engineering.yaml scores the capability model behind Microsoft's Platform Engineering Technical Assessment. The assessment is mostly organisational: it asks how staff and funds are allocated to the platform, how teams find and adopt it, how policy and access are governed, how resources are provisioned, what interfaces users get, and how success is measured. This page lists the items Scout asks, and every rule in that file cites an item number from the tables below.

Source ​

FieldValue
AssessmentPlatform Engineering Technical Assessment (60 minutes, multiple choice and multiple response; question text not published)
Framework versionPlatform Engineering Capability Model on Microsoft Learn (six capabilities: investment, adoption, governance, provisioning and management, interfaces, measurement and feedback; five stages: Initial, Repeatable, Defined, Managed, Optimized). Not versioned by Microsoft, current at the extraction date
Extraction date2026-11-25
Verification methodThe assessment landing page and the platform engineering hub page were fetched in full with the Microsoft Learn MCP microsoft_docs_fetch tool on 2026-11-25. The six capability pages and the principles, self-service, plan and application-platform pages were read through microsoft_docs_search excerpts of their stage tables and key sections the same day. Every collect.json property an automated item reads was checked against the header contract in src/collect/Invoke-Collect.ps1.

The one thing this enumeration is NOT ​

It is not Microsoft's question list. The assessment's questions are not published; its landing page gives only the length, format and a promise of tailored recommendations. The items below are Scout's reading of the published capability model, and the PLATENG-* IDs are Scout's.

The model places an organization at one of five stages for each capability. A stage is a description of how the organization works, so Scout does not try to name one. Each item is instead a practice the model describes, written so it can be answered Yes, Partial or No, and the score is the share of items met, not a stage per capability.

Sources:

  • [MODEL] Use the Platform Engineering Capability Model
  • [INV] Investment: Allocate budget and demonstrate ROI
  • [ADO] Adoption: Services, tools, and technologies
  • [GOV] Governance: Security and compliance policies
  • [PRV] Provisioning and management
  • [INT] Interfaces: Streamline provisioning and service requests
  • [MFB] Measurement and feedback: Establish feedback loops
  • [PRIN] Platform engineering principles
  • [SELF] Self-service with guardrails to empower developers
  • [PLAN] Plan and prioritize
  • [APPP] Refine your application platform
  • [ENGS] Apply software engineering systems
  • [DSS] Design a developer self-service foundation
  • [CASE] Case studies: Three platform engineering implementations

How the items are answered ​

Most items are questions about how the organization works, which no Azure API can read. They are manual rules: Scout lists them in assessment-questions.csv (or Export-ScoutAssessmentQuestion), and a person answers Yes, Partial, No or N/A. See Questionnaire answers. Where collected Azure data bears on a question, it is attached to the item as evidence, but the answer still decides the score. Items marked ✅ are automated and gated: they run only when the resources they read exist (or the data source was collected), so an estate without them reports the item Not assessed, never Passed or Failed, and an answer file cannot override them.

Only six of the 36 items can be judged from Azure data, and those only partly: Azure Policy assignments and their enforcement mode, direct user role assignments, budgets, infrastructure-as-code deployment records and YAML pipelines. Azure DevOps items need -IncludeDevOps; Azure Policy, role assignment and budget items need those reads to have succeeded. Dev Center catalogs, Dev Box pools, Application Insights and autoscale settings are attached to some questions as evidence only, because a platform can be built on other tools and their absence proves nothing.
