CAF Govern — enumerated source for the Cloud Governance assessment (Assess: CAF Govern) ​

Enumerated 2026-11-24. Verification method and limits are stated below — read them before quoting any coverage number from this page.

Framework version: Not versioned by Microsoft — the Cloud Adoption Framework Govern methodology carries no release number. The extraction date above (2026-11-24) is the version, per docs/frameworks/README.md; re-date this line when this file is next re-verified. This replaces the 2026-08-01 enumeration, which was built from the CAF Govern pages as read alongside the retired interactive assessment; every item below is now cited to a CAF Govern page directly.

Source: https://learn.microsoft.com/azure/cloud-adoption-framework/govern/

This is the AB#6811 enumeration for target #8 in the audit's fourteen-assessment programme (pmo/audits/AZURE-SCOUT-AUDIT.md §14): "Cloud Governance — policy data already collected … Policy compliance state is collected and scored by nothing." The audit's §8 Table 3 identifies this as the CAF Govern methodology — a different axis from the "Governance" design area that caf.governance.yaml already scores (that design area is part of Ready, covered in pmo/audits/AZURE-SCOUT-AUDIT.md §8 Table 2, not this document). Per DQ12, no caf.govern.yaml (or similarly named methodology file) is written until this enumeration exists.

Why this page was re-based ​

Microsoft deletes its interactive Cloud Governance assessment on the Microsoft Assessments platform in January 2027. Scout's earlier enumeration took the five-step process and seven categories from the CAF Govern documentation but described itself as "almost certainly built on" that assessment, whose question text was never published. That framing is retired. Scout's Assess: Cloud Governance (its Frameworks entry is CAF: Govern) is now defined by the CAF Govern methodology itself — the five-step process, the seven risk categories, the example risk register and the example policies Microsoft publishes — and is extended to everything those pages now describe, not only what the retired assessment asked.

The framework key inside the rule files stays Cloud Governance: the domain-score and report code groups on it, and the assessment keeps its name as an alias.

What CAF Govern is ​

Microsoft ships two distinct things under "governance," and this file is about the second one:

  1. caf.governance.yaml's subject — the Ready methodology's Governance design area, one of the 8 landing-zone design areas, already enumerated and scored (10 recommendations, ~70% coverage per the audit).
  2. This file's subject — the Govern methodology, one of CAF's seven core methodologies (Strategy, Plan, Ready, Adopt, Govern, Secure, Manage). Govern is a five-step continuous process — build a governance team, assess cloud risks, document policies, enforce policies, monitor compliance — applied across seven risk categories: regulatory compliance, security, cost, operations, data, resource management, AI. Step 1 is done once; steps 2 to 5 repeat.

Scout's rules therefore split along both axes. The seven categories are the seven scored areas that read Azure (RC, SC, CM, OP, DG, RM, AI). The process (steps 1 to 3, plus the audit, review and change-control practices around steps 4 and 5) is an eighth area, Governance Process (PROC), that no Azure resource can evidence: every item in it is a manual question, scored when the operator answers it (see Questionnaire Answers) and shown as Not assessed until then.

Verification method — and the limits ​

What was read (2026-11-24):

SourceWhat it gave
Build a cloud governance teamStep 1: team function, members, executive sponsor, authority, scope, RACI matrix
Assess cloud risksStep 2: identify, analyse, document, communicate, review; the twelve-field risk register and example list
Document cloud governance policiesStep 3: standard policy format and fields, distribution, review and change control; the sixteen example policies RC01 to AI02
Enforce cloud governance policiesStep 4: enforcement approach, per-category "Automate … governance" Azure facilitation, manual enforcement, example compliance checklists

Limits. The CGOV-* identifiers below are Scout's own; Microsoft does not number these items. Microsoft's example policy IDs (RC01 to AI02) are examples, not requirements, and are cited here only where a Scout rule reads the thing the example describes.

Shelf life. CAF Govern is actively maintained content (the AI category and the monitor and enforce pages were all extended recently); re-verify before quoting. The AI content-filtering built-in policies are preview definitions: their identifiers can change at general availability.

The enumeration ​

"Scout can evidence?" uses three marks: ✅ a rule scores it from collected Azure data; ⚠️ a rule scores part of it, or reads evidence but cannot score it; ❌ not observable from Azure, so the item is a manual question. Citations name the CAF Govern page anchor each item comes from.

PROC — The governance process itself ​

Citations: govern/ (step 1), assess-cloud-risks (step 2), document-cloud-governance-policies (step 3), enforce-cloud-governance-policies and monitor-cloud-governance (steps 4 and 5). All eleven are organisational — Scout reads the result of governance being enforced, never the process that produced the policy — so each is a manual question, scored when answered.

#ItemScout can evidence?
CGOV-PROC-01A cloud governance team is formally established with a charter, defined membership and cross-functional representation❌ Organisational
CGOV-PROC-02Governance policies are documented in a standard format (policy ID, category, risk ID, statement, purpose, scope, remediation, monitoring tool)❌ Organisational — Azure Policy objects carry a display name and description, not this authoring standard
CGOV-PROC-03Policies are distributed via a centralised repository, with compliance checklists for teams❌ Organisational
CGOV-PROC-04A compliance baseline was established and is tracked against over time❌ Scout collects a single point-in-time snapshot per run; no historical baseline is retained between runs
CGOV-PROC-05Noncompliance remediation has a defined timeline and escalation path scaled to risk severity❌ Organisational
CGOV-PROC-06A named executive sponsor grants the team its authority, and a RACI matrix assigns governance tasks❌ Organisational
CGOV-PROC-07A risk register exists with Microsoft's twelve fields and is reviewed on a schedule❌ Organisational
CGOV-PROC-08Every governance policy is linked to a risk ID and names the tool that monitors it❌ Azure Policy assignments carry no risk ID
CGOV-PROC-09Governance training is provided to the teams the policies apply to❌ Organisational
CGOV-PROC-10Internal audits (and external audits where required) validate compliance monitoring❌ Organisational
CGOV-PROC-11Policy change control: scheduled and event-based review, and a defined way to add, edit or remove policies❌ Organisational

The twelve risk-register fields CGOV-PROC-07 asks about are Microsoft's: ID, management status, category, description, probability, impact, priority, level (major threat, subrisk, risk driver), management strategy (mitigate, accept, avoid or transfer), management enforcement, owner and closure date.

What this means for the rule file ​

54 items: 26 are scored from data Scout collects, 28 are manual questions. The 28 manual items are the process (11), plus 17 inside the risk categories where the thing being asked is a human review, a setting in a tenant service Scout does not read, or a rule's condition that is not collected.

How the automated rules avoid a false Fail, because absence of evidence is not evidence of absence:

  • Rules that read policy assignments (RC-03, SC-07, CM-07, CM-08, DG-03, RM-03 to RM-05, AI-03) are gated on governance.policyAssignmentsAvailable: if the policy read failed they report Not assessed. They recognise direct assignments by built-in definition identifier (or, for an initiative, by its display name). An assignment made under a custom name, or a definition wrapped inside a custom initiative, is not recognised — the remediation text on each rule says so.
  • Rules that read Defender plans (SC-04, AI-04) are gated on the plan rows themselves: no rows means Not assessed, never "plans are off". SC-05 (PIM) is gated on governance.pimEligibilityAvailable, which is always false today.
  • Rules that compute a percentage (CM-06, DG-04, DG-05) report Unknown when there is nothing to measure a percentage of (no budgets, no storage accounts), never a 0% Fail.
  • Rules that read Monitor or Storage data need those categories in the assessment's collect (Monitor for OP-05/OP-06, Storage for DG-04/DG-05). A saved collect made without them is refused up front by the collect-provenance check rather than scored as empty.

The Governance Process area is excluded from the headline score until at least one of its questions is answered, exactly as a manual rule in any other area is. A tenant that answers none of them is not penalised for it; it is simply shown Not assessed.

Management/PolicyComplianceStates remains the single largest lever: RC-01, SC-02 and OP-01 all resolve to it, and it is populated only when the collect is run with -IncludePolicyCompliance.
